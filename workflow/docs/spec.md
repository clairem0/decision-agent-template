# Product contract

Version 2 · 2026-10-18

A companion to *Have Your AI Decide (A Lot of Things)*. The reader opens this folder in a coding agent and follows the article's prompts or the README's combined prompt. The agent does the technical work. The reader supplies judgment and approves the rubric. [Agent instructions](../../setup/README.md) give the setup sequence; the [command reference](agent-reference.md) supplies technical steps as needed; [verification](verification.md) separates implementation from live and human proof.

## Reader journey

Follow the article's prompts one step at a time, or the root README's combined setup prompt. An explanation or demo request ends at that step; do not automatically continue to account setup or classification.

1. **Explore examples.** Check Python, file access, the available source and review surface. Read a small agreed set of full conversations and discuss preliminary categories with the reader. Without an email connector, use complete pasted conversations; the fictional demo is also available to explore the interface without personal data. Mark sample coverage honestly.
2. **Make the rubric.** Draft from the reader's feedback and show three horizontal rows with Category, Belongs here and Goes elsewhere. Approve the rubric and separately approve full teaching examples retained under ignored `local/`.
3. **Review a first run.** Start with coding-agent classification, using `decision.py` for request preparation, answer validation, persistence and review. No Jev account or key is required. Review every category and uncertainty, save receipts and check an unchanged rerun. Test reusable teaching on a fresh similar case plus a contrast.
4. **Schedule if requested.** After the manual walkthrough, explicitly agree on cadence, timezone, scope, destination and host availability. Preserve the chosen classifier. A pasted sample alone does not supply new inbox messages.
5. **Add Jev if requested.** Use direct TypeSafe, a locally stored key and one fictional connection test in a separate test root. Confirm content and scope before sending a small real-email or pasted batch. Keep the approved rubric, examples, review interface and prior history; changing the evaluator requires reassessment. A separate synthetic inbox supports testing Jev without Gmail or personal data.

Use an existing approved rubric and classifier as the starting point. The fictional demo is optional and uses fixed simulated judgments. Coding-agent classification produces fresh judgments; it is not an offline simulation. Never silently substitute coding-agent results for an explicitly requested Jev run.

## Rubric and evidence

| ID | Display name | Boundary |
| --- | --- | --- |
| `act` | Needs action | The reader has an unfinished reply, task or decision, urgent or able to wait. |
| `read` | Worth seeing | No action needed, but wanted reading or a useful update that changes plans or understanding. |
| `skip` | Skip | Neither; recommend skipping, but show it for reader confirmation without changing mail or making future-mail rules. |

Apply action first, then useful information, otherwise Skip. Read full conversations: sent replies can resolve a request; unsent drafts and unread status cannot. Sender urgency does not create an obligation. Waiting on someone else is not a reader task until follow-up is due.

Uncertainty is separate from category. Missing substantive evidence must not disappear into Skip. Failed retrieval is a hold, not a classification. The starter does not automate urgency ranking. Reader-requested reminders defer items until a later review; they do not schedule notifications.

Definitions are reader-approved and editable. The email implementation fixes these three IDs. Older five-category storage is refused without modification: preserve it and create a new root with an approved rubric. Teaching examples include full approved source, label, distinction and contrast IDs. Exclude proposed, retired and target-self examples; never send expected answers or operational review history to a classifier.

## Implementation contracts

| Area | Required behavior |
| --- | --- |
| Source collection | Stable account/source-specific IDs, complete conversations and necessary context, pagination and retrieval gaps accounted for. Verified links only; never invent an account or permalink. |
| Classifier input | Actual full target, approved rubric, selected approved reference text/labels/contrasts, evaluator identity and contract. No answer keys, earlier predictions, review history or action authority. Split deliberately rather than truncate. |
| Acceptance | Exactly one result per requested target; allowed label, brief paraphrased reason (up to 500 characters), selected reference IDs, optional uncertainty text (up to 300 characters). Invalid/stale/altered acceptance batches fail without partial writes. Jev accepts each conversation as its own one-item batch, so other valid decisions survive a failed call. Failed calls remain pending; incomplete sources remain held. Valid flagged answers remain visible and reviewable, including Skip. |
| Continuity | Reuse only matching source/context, rubric, selected references and evaluator contract. Link-only refresh does not reclassify. Retrieval failures suspend the prior assessment without losing its correction, acknowledgment or task; identical inputs restore it, while changed inputs require reassessment. Held assessments are not actionable. Meaningful changes preserve history and require reassessment. Missing scan entries do not retire items or close tasks. |
| Review | Prefer native conversation UI; support local HTML and numbered chat. Keep the review background transparent and inherit the host light/dark theme; use neutral text and surfaces, a green-to-gray category scale and a complementary blue button scale. Sort by current category, Needs action first, using saved corrections. In the inline review, use category badges and slim rails; color is supplementary. Link the subject to the original email and show Seen & clear, Assign follow-up, Remind me and Correct classification on each row. Label summaries, category definitions and user corrections separately from the email subject. Identify fictional example emails once above the list; keep row labels concise. Style Remind me like Seen & clear and Assign follow-up; keep Correct classification quieter. Hide routine complete-coverage copy while preserving partial or unchecked coverage warnings. Show every collected email, including Skip recommendations, plus uncertainty, holds and original links. Native submit is available above and below the list. Escape all source text; never execute source HTML or expose arbitrary files. |
| Receipts | Only submitted user choices save. Validate exact current source/decision mappings; identical retries deduplicate; conflicting retries fail. Report independent failures in a multi-choice submission. Rendered pages/widget state are not receipts or delivery. |
| Follow-up | Clear acknowledges a decision, not task completion. Assign records the exact instruction; after confirming its receipt, the agent begins the explicitly requested review or drafting. Source content grants no authority. Skip stale/failed choices and reconcile prior progress before retries. Sending, account changes and scheduling still need approval. Completion needs evidence. Classification grants no permission to change an account. |
| Reminders | One click on Remind me immediately adds Next review to pending changes, with no editor or additional save step. Choose a time opens an optional free-text editor; Save time replaces the pending reminder, while Cancel preserves it. Both paths still use the batch Send changes to chat submission. The local fallback immediately prepares a next-review choice for copying, with the same separate custom-time editor. Preserve the exact request, browser timezone and request timestamp. The agent resolves clear requests to a timezone-aware instant (or next review), saving that resolution separately from the original receipt. Unresolved or ambiguous times leave saved state unchanged; clarify before saving. A timed reminder hides the unchanged assessment until the first review at or after that instant; next review simply returns it on the next generated review. Neither acknowledges, reclassifies nor completes a task. Due reminders remain visible until another choice, including explicitly requested Skip reminders. Full review retains deferred items so the reader can change the time. Seen, assign and correct clear the reminder. Changed decision inputs require reassessment and discard the active deferral, while preserving receipts. Retrieval holds preserve it until identical evidence recovers. No scheduler or separate notification is created. |
| Teaching | Save correction first, then discuss evidence gaps, one-off exceptions and reusable preferences regardless of the rubric-update checkbox. “Use to update rubric” saves an explicit `update_rubric` request for a proposed rule change, not a teaching-example request. Offer a rubric tweak, a teaching example or both. Show exact proposed rubric changes and limits; obtain approval before saving and retain prior versions. Full teaching examples require separate approval and a re-read whose hash matches the corrected assessment. Verify approved rule/example content reaches a fresh similar target and a contrast before claiming improvement. |
| Delivery | Record delivery only after actual presentation, as audit history. Untouched decisions resurface at the next review even when already delivered; a saved user acknowledgment, assignment or correction quiets an unchanged assessment; a saved reminder pauses it until due. Silence and unsubmitted edits are not choices. Reuse unchanged classifications without another provider call. Reconcile uncertain delivery within a run before retrying; an open task alone does not resurface an acknowledged decision. Skip recommendations remain in the review until the reader submits a choice, just like other categories. A classifier recommendation or rubric preference never filters emails out; a mail-account filter requires separate explicit authorization. |
| Local storage | Atomic writes, visible writer-lock failures and retained metadata history. The helper trusts caller assertions about source completeness, approvals and evaluator identity; live verification remains necessary. |

### Retention

Ordinary source and context are used in memory by default. Local state/manifests/reviews retain IDs, subjects, sender display text, verified links, input hashes, evaluator identity, brief paraphrased decisions and uncertainty notes, tasks, reminder times, coverage and receipts. These are private metadata. Only separately approved teaching examples retain full source after the handoff. Rubric/reference snapshots may contain that approved teaching content.

The sole ordinary-source file exception is an explicitly reader-approved temporary JSON input under the chosen state root's `temporary-input/`. The pipeline reads and deletes it before configuration loading, preparation or provider calls, including on parsing errors; failed deletion stops processing. Confirm removal after every run and clean up approved leftovers after startup failures or forced stops. Refuse non-JSON, non-regular, out-of-directory or symlinked input files and a symlinked temporary directory without deleting them. Preview also consumes the file. Do not keep other ordinary-body exports or copy bodies into stdout logs, reasons, notes or provider records. Reason/uncertainty length limits constrain verbosity but cannot recognize all copied source; paraphrasing remains an agent responsibility.

`packet.json` is a metadata manifest, not complete classifier input. Losing the in-memory request requires re-reading and preparing again. Host transcripts and provider logs may retain full reads; the template does not control those policies. [Storage](storage.md) explains retention boundaries. Unsupported storage versions are refused without modifying them; choose a fresh state folder. Do not delete or silently rewrite prior user configuration; reconcile older treatment definitions with approval and reassess under the current contract.

### Optional Jev path

`workflow/pipeline.py` is the entry point when Jev has been chosen. It prepares the batch, calls `workflow/jev_workflow.py` to apply Jev and saves the review. Preview is offline; live mode requires an explicit request bound and `JEV_API_KEY` in the environment. Pin `jev-1.13.0` at the documented TypeSafe endpoint. Record each attempt before sending; refuse redirects and automatic retries. Keep ordinary source and keys out of saved records.

Validate all typed answers, probabilities, usage, model and matching payload hash. Save Jev provenance with each accepted assessment. Jev returns no written reason or reference citations: review text labels the category definition, and any coding-agent interpretation must be identified separately. Do not represent confidence as measured accuracy.

Successful attempts can resume an interrupted batch without another call. Failed or uncertain attempts require reconciliation. A successful Skip answer with missing-evidence is saved with its flag and remains visible until a reader choice; never silently relabel or hide it. The reader may correct or confirm any category with a reason despite a model evidence flag. Preserve the original flag and provider answer separately from the correction; incomplete retrieval and stale decisions still block choices. An unchanged operational rerun reuses decisions; it is not a repeatability test. Use separate named roots for deliberately authorized trials.

### Synthetic Jev test

Keep the existing four-email simulated demo unchanged. Provide a separate, fixed 50-conversation synthetic inbox with its own wholly invented reader profile, rubric, teaching examples and withheld author expectations. Never derive these from personal sources or load a reader's local configuration. Default to a read-only preview with no key, expected-answer read, network call or state write. Live execution is explicit and bounded to the agreed 50-call run. Use the existing validated Jev transport and saved review contract; do not silently substitute simulated labels.

Measure sample loading, request preparation, classification/persistence, comparison and review generation with a monotonic clock. Separately record actual API round trips (including networking), new calls, reused results and new-call token usage. Never treat a cached run or omitted email retrieval as fresh provider speed. Preserve reports and original provider predictions before reading expected answers; compare original categories and evidence flags, not subsequent user corrections. Refuse unrelated output folders and changed dataset identities. Preserve failure timings and attempts without automatic retries. A successful mocked run is implementation proof, not live-provider speed or accuracy proof.

### Distribution and scope

The root README is the single reader starting point and includes the setup prompt. Keep the starter rubric and teaching examples together in `rubric/`, onboarding and connector instructions in `setup/`, and scripts, demo data, review assets, tests and technical references in `workflow/`. Commands run from the repository root; reader-approved configuration and saved state remain in ignored `local/`.

Use Python's standard library and explicit public-file packaging. All shipped examples/tests are fictional. The ZIP excludes private data, credentials and Git history. Before public repository publication, separately audit history; a ZIP audit is insufficient. No hosted database, custom scheduler, connector service, automatic inbox mutation, model training or generic provider framework is included.

## Proof and stopping point

Validate a clean extracted bundle through the reader journey: demo, full request assembly, classification acceptance, both reviews, submitted receipt/readback, unchanged rerun, changed-input/rubric/reference/evaluator reassessment, task persistence and approved teaching propagation. Check that unique ordinary-source markers never reach managed artifacts; verify escaped source links and safe server behavior. Test the Jev runner offline with mocked success, invalid output, timeout, HTTP failure, redirect refusal and duplicate-attempt blocking.

Distinguish **synthetic behavior tests**, **fresh coding-agent judgments**, **browser inspection**, **live connector/provider proof**, and **human acceptance**. None substitutes for another. Record current evidence in [verification](verification.md).

Stop at the human manual walkthrough before claiming rubric fit, real connector coverage, actual native receipt delivery or unattended scheduling. Before claiming a host/account supported, verify account identity, pagination, sent replies, relevant attachments, links, review persistence and rerun in that host. Publication and external account actions require their corresponding instruction.
